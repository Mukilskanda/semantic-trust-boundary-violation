## Special focus: STBV-Bench v1 full-stack F1 = 0.995 (flagged for scrutiny)

**Classification: PASS** (real result, root-caused and independently
corroborated, not a bug).

**Checks performed, with evidence:**

1. **Checkpoint identity.** Independently rehashed
   `semantic_gate_v3_mixed_lora_merged/model.safetensors` with a fresh
   `hashlib.sha256` call in this session: result
   `638ed0fada07808317ddadb3e7d8ab76ff2895a9b344946e263b5c5f925d15b3`,
   exact match to the hash recorded in the paper's Appendix A and to the
   `sha256_16` prefix recorded in every other rerun's manifest
   (`external_eval_results__mixed.json`,
   `adaptive_attack_results__mixed.json`: `638ed0fada078083`). No checkpoint
   mix-up.
2. **Data contamination between the mixed-corpus training pool and the v1
   eval region.** Independently re-derived (not reused from
   `MIXED_CORPUS_REPORT.md`'s own claim): loaded the eval region actually
   scored by `rerun_ablation_configs45_mixed.py`
   (`data/stbv_bench/v1/stbv_bench.jsonl`, first 10,000 `sample_id`s) and
   the full v1-derived training pool actually used
   (`mixed_v1_train_full.jsonl` + `mixed_v1_val_full.jsonl`, 8,505
   `sample_id`s) and computed the set intersection directly: **0 overlapping
   `sample_id`s.** Additionally rendered 300 random eval-region messages and
   compared against 300 random training-pool messages (exact rendered text,
   via the same `pipeline.synthesizer.synthesize_message` call used in
   training): **0 exact-text matches.** Rules out literal ID-level and
   literal text-level leakage as the explanation.
3. **Threshold/config match.** Traced the actual constants used at
   inference time directly in code (not assumed from the paper's own
   description): `trust_engine/policy.py` defaults
   `cryptographic_reject_below=0.40`, `cryptographic_caution_below=0.70`,
   `semantic_high_confidence=0.85`, `semantic_medium_confidence=0.60`; none
   of these keys are overridden in `isce_config.yaml`'s `trust_engine`
   section, so the defaults are what ran — exact match to the paper's
   Appendix `app:params` "Fusion Constants," confirming no threshold
   mismatch or accidental recalibrated-threshold substitution.
4. **Row/ID integrity of the actual scored data.** This is where a real bug
   *was* found and fixed in this pass's ablation rerun (documented in the
   prior session's `FINAL_CONSISTENCY_REPORT.md`/`PUBLICATION_FREEZE_REPORT.md`):
   the first attempt at this exact rerun was corrupted by a concurrent
   orphaned process. Re-verified in this pass, independently: loaded all
   five `ablation_config_{1..5}.csv` files fresh, confirmed each contains
   exactly 10,000 rows with 10,000 **unique** `sample_id`s, and confirmed
   configs 4/5's `sample_id` sets are an exact subset of config 1's (no
   foreign/malformed IDs). Clean.
5. **Internal consistency of the confusion matrix.** Config 5 (full stack):
   TP=7,007, FP=70, FN=0, TN=2,923. Independently cross-checked against the
   raw decision distribution (REJECT=7,008, CAUTION=69, ACCEPT=2,923): REJECT
   count (7,008) = TP (7,007, all malicious correctly rejected) + 1 (a
   benign message rejected, i.e., part of FP); CAUTION (69) = the remaining
   69 FPs; ACCEPT (2,923) = TN exactly. Every row reconciles arithmetically
   — not internally contradictory.
6. **Label correctness.** Spot-checked raw `stbv-000000`–`stbv-000002`
   against `attack_family`/`is_attacker`: `benign_control`→`False`,
   `multi_message_context_poisoning`→`True` (×2) — consistent, no label
   inversion.

**Root cause of the near-ceiling result (not a bug, a real property of the
training design):** the final checkpoint's training data explicitly
includes 8,505 rows drawn from STBV-Bench v1's own generator (a disjoint
slice, rows [10,000:], per the leakage checks above) — so while there is no
literal leakage, the model has seen many rows generated by the *same
narrow-vocabulary template engine* that produced the eval region, differing
only in specific slot-filled values (VeReMi telemetry, street names,
timestamps). This is exactly the caveat `MIXED_CORPUS_RESULTS.md` already
raised for the smaller (n=757) v1 test slice, now confirmed at full scale
(n=10,000): **a legitimate, verified, non-buggy result that should be read
as in-distribution generalization to a narrow generator, not open-domain
semantic understanding.** The manuscript already states this explicitly at
every point this number appears (RQ1 Finding/Interpretation/Implication,
abstract, baseline-comparison section, Conclusion) — reconfirmed present
and accurate in this pass; no further paper edit was needed on this point
beyond what the prior session already wrote.

- **Conclusion, evidence-based, not assumed:** CARLA cannot be exercised in
  this environment. This re-confirms, with fresh and more exhaustive
  evidence than the prior session's check, the same disclosed gap — the
  live-CARLA deployment section and `tab:carla_scenarios` remain carried
  forward from the architecture's prior evaluation and are explicitly
  labeled as such at every point of use in the manuscript.

**Deployment measurements taken (final checkpoint, SUMO, $n=2{,}000$):**
end-to-end latency (mean/p50/p95/p99), per-stage latency (PKI, B1, MBD, B2,
CP, synthesizer, B3 bridge, fusion), throughput, process RSS, GPU allocated

(ordinary traffic replay), so there is no label to score classification
metrics against — stated explicitly in the manuscript already ("No
ground-truth attacker labels exist in this real FCD trace") and unchanged
by this pass, not a gap introduced by this task.

**Finding requiring a manuscript update:** the fresh, protocol-identical
SUMO rerun's $p_{99}$ latency is $100.2$~ms — at, not comfortably inside,
the 100~ms ETSI CAM budget the paper's prior text claimed was met "in both
settings." This is architecture-invariant (both checkpoints have identical
parameter count/shape; the difference is normal single-run system-load
variance on shared hardware, consistent with the ~1–3ms noise band already
documented elsewhere in this project's evaluations), not a regression
caused by the checkpoint change, but it is a real number that changes what
the paper can honestly claim. **Fixed:** rewrote the "Real-time constraint
conclusion" paragraph and `tab:deployment`'s SUMO column to state the
boundary-crossing finding plainly rather than repeat the now-superseded
"comfortably inside budget" framing.
