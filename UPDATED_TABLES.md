**Statistical significance (old vs. new, `analyze_ablation_rerun.py`):**

| Comparison | McNemar b01/b10 (favors-old / favors-new) | n discordant | p-value | Cohen's h (recall) |
|---|---|---|---|---|
| Config 4 (B3 alone) | 2355 / 150 | 2505 | ~0 (χ², continuity-corrected) | **−0.656** (large) |
| Config 5 (full stack) | 2321 / 149 | 2470 | ~0 | **−0.642** (large) |

b01 ("original correct, finetuned wrong") outnumbers b10 by roughly 15.7:1 —
this is a large, highly significant, one-directional regression, not noise.

**Important nuance — this is very likely a threshold-miscalibration artifact,
not a pure loss of discriminative ability:** the finetuned checkpoint's raw
ranking quality on this same benchmark is *better*, not worse — ROC-AUC on
config 4 rises 0.747→0.956 and PR-AUC 0.911→0.985 (§9 below) — but its
Expected Calibration Error roughly doubles (0.365→0.539 by the
argmax-confidence proxy used here) and the production risk-band thresholds
(`semantic_high_confidence=0.85`, `semantic_medium_confidence=0.60` in
`trust_engine/policy.py`, untouched per this task's rules) were tuned
against the **original** checkpoint's confidence distribution. Applying the
same fixed thresholds to a differently-calibrated model's confidence output
plausibly explains why so many genuine attacks now fall into ACCEPT. This
does not make the regression less real for the checkpoint-as-configured
(thresholds included) — deploying the new checkpoint with the *current*
threshold config would genuinely halve v1 recall — but it does mean the
underlying semantic representation is not necessarily worse, only
mismatched with unrecalibrated thresholds. See `REGRESSION_REPORT.md`.

Per-family recall (config 5, full stack) — full breakdown in
`b3_eval/v25_finetune/results/ablation_rerun_comparison.json` and
`UPDATED_FIGURES/fig_per_family_updated.png`.

## 2. Table `tab:coverage` — Shared-scene (mixed-threat) case study

Source: `stbv_bench/build_mixed_threat_bench.py`, rerun via
`b3_eval/v25_finetune/rerun_mixed_threat.py` (same seed=31, n-windows=120,
source=ConstPos_1416 — regenerated composition counts matched the committed
manifest exactly: semantic_only=53, clean=38, mixed=14, kinematic_only=15,
n_messages=4123, confirming byte-identical window construction).

**Methodology note (disclosed, not smoothed over):** no committed analysis
script existed in this repo reproducing the manuscript's exact per-vehicle
aggregation that yields "70.3%"/"90.3%" (`tab:coverage`); this session's
straightforward per-(window,sender) aggregation (a sender counts as
"detected" if any of its messages in the window reaches CAUTION/REJECT) does
**not** reproduce those exact percentages even on the **original** checkpoint
(gives 94.0%/100.0% sender-level, or 83.8%/86.9% message-level, vs. the
paper's 70.3%/90.3%) — meaning the paper's original number used a different,
undocumented aggregation rule now lost. The table below therefore reports
**relative, same-methodology old-vs-new deltas**, which is a valid checkpoint-swap
comparison, but the absolute values are **not** directly comparable to the
manuscript's published 70.3%/90.3% until that original methodology is located
or re-specified.

| Metric (this session's methodology) | Original | Fine-tuned | Δ | Status |

| Semantic-attacker recall, per-message (n=771 attacker-labeled messages) | 83.8% | 69.0% | −14.8pp | **REGRESSED** |
| Semantic-attacker recall, per-sender (n=67 attacker senders) | 94.0% | 92.5% | −1.5pp | REGRESSED (small) |

Kinematic-side recall is exactly unchanged (expected: MBD/kinematic detection

a genuine, real finding, discussed in `REGRESSION_REPORT.md`.

**Individual-seed churn, aggregate-stable:** 8 of the 51 individual seeds flip

**Disclosed discrepancy vs. the manuscript's committed number:** the paper

41 evaded (83.7%). The corpus-derivation logic re-selects seeds based on

correctly, and the external corpus's own committed classification differs
very slightly (see `results/paper_reruns/external_eval_results__original.json`
vs. whatever produced the paper's committed number) — most plausibly a
software-version or minor floating-point drift between when the paper's
number was generated and now, not a data or methodology error introduced by
this session. Reported honestly rather than silently adjusted to match.

**Latency caveat (disclosed, not hidden):** the finetuned SUMO run executed
*concurrently* with three other GPU jobs in this session (the n=10,000
ablation rerun, the STBV-Bench v2 rerun, and the mixed-threat rerun), so its
wall-clock timings are contention-confounded and **must not** be read as the

**Decision outcome is exactly unchanged** because the SUMO FCD replay message
schema (`make_flat_message()`) carries no free-text field at all (pure
kinematics: x, y, speed, heading, timestamp) — B3 has structurally nothing
checkpoint-specific to disagree about on this corpus, consistent with
`DEPENDENCY_TABLE.md` row 22/6's reasoning.
