# Reviewer #2 Objection List (Pre-Edit Audit)

Written before making any further changes this pass, as an honest "try to reject this paper" exercise. Each objection is marked FIXED (this pass), ALREADY ADDRESSED (prior pass), or OPEN (genuine, unresolved limitation, stated as such rather than hidden).

1. **"The abstract spends its word budget on benchmark names, not on what's architecturally new."** OPEN going in, being addressed this pass — see revised abstract.
2. **"Architecture is introduced almost incidentally between the threat model and the results — I had to hunt for what's actually novel about B1→B2→B3→fusion as a *pipeline design*, not just four component names."** FIXED this pass: new "Why Three Trust Layers?" subsection gives the reader a memorable, one-line question per layer.
3. **"Table I's near-zero B1/B2 rows look like the architecture doesn't need two of its four stages."** ALREADY ADDRESSED (prior pass): ABLATION_AUDIT.md + ITE-Bench demonstrate each layer at 1.000 in-class recall / 0.000 out-of-class, with McNemar-confirmed zero-cost layering.
4. **"STBV-Bench v1's near-ceiling F1 is an in-distribution artifact of the same generator family the checkpoint was partly trained on."** ALREADY ADDRESSED: v2.5b (template-disjoint, zero-overlap-verified) is reported as the more conservative, deployment-relevant number (F1 0.945), and the paper explicitly says v1's F1 shouldn't anchor deployment claims.
5. **"DeBERTa-v2 justification reads as post-hoc rationalization — the backbone comparison in the appendix doesn't actually favor it."** ALREADY ADDRESSED, and the paper says so plainly: "no evidence favoring a switch," not a manufactured win. This pass expands the justification with the encoder-vs-LLM latency argument stated more explicitly.
6. **"CARLA results are unstable across runs — how do I trust Table IV at all?"** ALREADY ADDRESSED: disclosed explicitly per-scenario, root-caused to CARLA's unseeded traffic manager via code-path separation (not the synthesizer fix), not smoothed over.
7. **"Adaptive-attack numbers are from a different (prior) checkpoint than the rest of the paper — this is a real inconsistency."** OPEN, disclosed: rerunning requires the full 51-seed/10-round campaign, out of scope for this pass; the paper labels this explicitly at every occurrence rather than presenting it as current.
8. **"ITE-Bench's B2 (behavioral) attacks are synthetic constructions, not real trajectories — how do I know they generalize to real driving kinematics?"** OPEN, disclosed in ABLATION_AUDIT.md §5: this is a genuine scope limitation. ITE-Bench demonstrates the *mechanism* (each layer contributes within its threat class given a protocol that can exercise it), not that synthetic B2 attacks match real-world kinematic attacker capability at VeReMi's fidelity.
9. **"Figures are inherited from earlier evaluation passes and some are stale relative to the final checkpoint (e.g., the ablation summary plot)."** PARTIALLY OPEN: the stale ablation figure is now disclosed directly in its own caption (prior pass) rather than left silently inconsistent with Table I. No new figures were generated this pass or any prior pass — this environment has no plotting/diagram-generation tooling invoked in this session; regenerating `fig_ablation_summary.pdf` or producing a cleaner architecture diagram requires either a plotting script run (not attempted this pass, see below) or new artwork this environment cannot originate from nothing. Stated as an open item, not silently worked around.
10. **"No real baseline outside this project's own ablations is discussed in the compressed main text — where's the comparison against, e.g., a pure ML anomaly detector or an existing MDS?"** OPEN, and a legitimate gap: the original (longer) manuscript had a baseline-comparison section (TF-IDF/LogReg, zero-shot LLM, regex) that was moved out of the compressed conference version for space (Part 3 scope instructions in an earlier pass). This is a real trade-off of the compression, not an oversight — noted here for the record.
11. **"Deployment realism: CARLA/SUMO tests use one town, one hardware config, small message counts (400/2,000) relative to STBV-Bench's 10,000."** ALREADY ADDRESSED: the paper states this scope limitation directly in the relevant subsections; not something this pass can close without new large-scale infrastructure.
12. **"Reproducibility: page count still hasn't been verified against a real LaTeX compile."** OPEN, unchanged: no LaTeX toolchain available in this environment across every pass of this session. Stated in READY_FOR_SUBMISSION.md as the top outstanding item.
13. **"The paper still reads somewhat benchmark-centric in the Results section headers and transitions, even with 'what this proves' framing."** FIXED this pass where feasible: tightened transitions and reduced dataset-construction detail further in the Methodology section (see diff in FINAL_CHANGELOG.md).

## What this pass does NOT attempt, and why

- **No new experiments or reruns of CARLA/SUMO/VeReMi.** Per Part 12's own instruction ("if new bugs are discovered, fix them; re-run affected experiments") — no new bug was found this pass in any of these three. Rerunning without a discovered defect would violate the standing freeze policy from earlier passes in this session and risks manufacturing the appearance of new evidence where none exists.
- **No expansion of ITE-Bench's attack diversity.** The existing ITE-Bench already demonstrates the required property (each layer excels within its own threat class, zero-cost layering, McNemar-confirmed) cleanly. Adding more attack families without a specific gap they'd close risks diminishing returns for a large time cost; this is flagged as a legitimate future-work item rather than attempted for its own sake.
- **No new or redesigned figures.** This environment has no diagram/plot generation invoked this session; all figures are existing repository artifacts. Claiming a "redesigned, cleaner figure" without actually producing new artwork would be a fabrication. This is stated plainly as an open item.
