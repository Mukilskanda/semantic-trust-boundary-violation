## Figures NOT regenerated this pass, and why

The request asked for up to 12 new/regenerated figures (architecture overview, existing-vs-full-STBV comparison, layer-contribution flow, confusion matrix, ROC, PR, CARLA latency timeline, per-stage latency, attack-family heatmap, per-family grouped bar chart, decision-transition diagram, deployment summary). Of these:

- **Architecture overview, existing-vs-full-STBV comparison** -- already exist as `fig_architecture` and `fig_whyfail` (a real, concrete worked-example comparison with real trust scores, $T_{Decision}{=}0.730$ vs.\ $0.240$), both from the current final checkpoint. Not regenerated: no new data would appear in them; the underlying numbers are unchanged by this pass's real reruns (verified in `FINAL_CONSISTENCY_AUDIT.md`).
- **Confusion matrix, ROC, PR** -- already exist as `fig_v25b_confusion_grid` and `fig_v25b_roc`, both built from the current final checkpoint's real per-sample scores (ROC AUC 0.9892, PR AUC 0.9896, confirmed in a prior pass's `scratch_latex_audit.py`-verified cross-check). Recomputed this pass as part of the audit (Section "F1 vs precision/recall consistency" in `EVALUATION_AUDIT.md`) and confirmed unchanged -- not regenerated as new image files since the source data did not change.
- **Per-stage latency** -- already exists as `fig_sumo_stage` (a real 3-panel latency timeline/breakdown/throughput figure from actual SUMO deployment logs, not synthetic). Not regenerated: this pass did not rerun the SUMO deployment (out of scope; no evidence the deployment logs are stale, and Part 8 confirms consistency without requiring a rerun of every prior experiment when the checkpoint under test for those experiments is unchanged).
- **CARLA latency timeline with rolling average/95th percentile/ETSI threshold** -- **not built this pass.** The existing CARLA deployment logs (`b3_eval` CARLA run artifacts referenced in the paper's Section V-C) report only aggregate statistics (mean 80.1ms, $p_{95}{=}97.2$, $p_{99}{=}110.8$ms, throughput, drop count) in the current repository state, not a per-message index-vs-latency log suitable for a timeline plot with a rolling average overlay. Building this figure would require either (a) locating a raw per-message CARLA latency log if one exists uncatalogued in the repository, or (b) rerunning the live CARLA deployment to capture one -- the latter requires a running CARLA server and simulation, out of scope for this pass's time budget. **Not fabricated as a placeholder.** Documented here as a genuine gap for a future pass with CARLA available.
- **CARLA trust-score evolution** -- **cannot be generated**, for the same reason the paper's Section V-C already states no dedicated deployment-architecture/trust-evolution figure was produced: the live CARLA harness logs per-scenario decisions (Table `tab:carla`) but not a continuous per-message trust-score trace suitable for a time-series plot. Explaining this honestly, per the request's own fallback instruction, rather than fabricating a curve.
- **Deployment summary (latency/throughput/memory/GPU)** -- already exists as `fig_sumo_stage`'s multi-panel figure plus the in-text CARLA/SUMO throughput-latency-GPU numbers (Section V-C); not duplicated into a second figure showing the same real numbers a second way, per Part 6's "remove/avoid uninformative figures, same conclusion shown elsewhere" instruction.
- **Layer-contribution flow diagram, decision-transition diagram** -- judged, on the "what unique insight does this figure provide beyond the existing architecture diagram and ablation table" test, to visualize information Table `tab:ablation` and Fig.~`fig_architecture` already convey (the six-configuration progression is now a single real table, and the escalation-only Caution$\to$Reject transition is stated as a verified textual fact in Section V-B, traced to a bit-for-bit confusion-matrix identity in `EVALUATION_AUDIT.md` Finding 5) -- not built as a separate figure to avoid the exact redundancy Part 6 warns against.
